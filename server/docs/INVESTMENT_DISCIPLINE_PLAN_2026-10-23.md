# 投资纪律功能整改方案

日期：2026-10-23。范围：FinUnityServer、FinUintyWeb、FinUnity Android。本轮落地的是本地私有初始数据批次、可重复生成工具及验证；下文功能为后续实施方案，未发布、未启用自动通知，也未操作线上账号。

## 产品目标与当前缺口

用户设定一次计划，打开产品即可看到今天需要做、暂时不应做和等待条件的事项；实际成交只记录一次，持仓、现金、月度额度及后续任务同步更新。已确认的信息持续有效，只对新增且影响当前动作的缺口提问。

目前系统有账本能力，还没有完整投资执行流程：

| 已读代码 | 当前行为 | 需要解决的产品问题 |
| --- | --- | --- |
| `src/finunity_server/contracts.py` 的 `HoldingItem`、`TransactionItem` | 持仓快照与流水可分别写入，有币种及版本 | 缺少计划版本、执行单及订单/成交/结算状态，不能追溯某笔交易占用哪项计划额度 |
| `src/finunity_server/v1_api.py` 的 `ledger_summary` | 持仓和现金快照决定资产，流水不会改变现金快照；基础币种以外分开显示 | 记录买卖后仍需另改资产；无法据此可靠判断剩余资金；不能将“分币种显示”误称已完成全家庭换算 |
| `tests/test_ledger_consistency.py::test_transactions_do_not_mutate_cash_snapshots` | 当前测试明确固定上述快照行为 | 后续改造必须做版本化迁移，不能直接让旧流水重放一遍导致历史现金重复扣减 |
| `src/finunity_server/store.py::commit_holding_import` | 已有导入原子提交、幂等、来源引用 | 应复用其事务、版本冲突及重复请求约束，扩展到成交与资金变更 |
| Web `src/holdingImport.ts`、`src/GuestImportPanel.tsx` | 有截图/表格预览、本人录入数据确认带入 | 缺少交易预览、计划绑定、执行差异与今日任务，不能把CSV模板当完整初始状态恢复格式 |
| Android `HoldingLedgerRepository`、`Transaction` | 已有本机账本、来源指纹和交易类型 | 可复用领域思路，但需与服务端定义统一，避免两端各算一套不同额度 |
| Android `RecurringRuleRepository`、`RecurringRuleWorker` | 定期生成收入/支出流水 | 投资定投只能生成待办/预计，不能到日期就生成“买入成功”或自动扣减真实余额 |
| Android `ReviewReminderWorker` | 每30天月度复盘通知 | 不是交易日每日计划，也没有价格、财报窗口和提醒去重状态 |
| Server README、参考数据服务与 `holdings:refresh` | 默认参考行情带STALE标识，另有可配置持仓刷新接口 | 刷新入口存在不等于生产已接入实时数据；陈旧/参考/时间不明的价格不能触发“可以买”通知 |

因此先补齐数据及成交一致性，再实现每日任务和提醒。大模型负责把自定义文字计划整理成可检查的规则草稿、解释计算结果；金额、约束判断和任务状态由明确规则计算。

## 本次初始记录的边界

私有初始批次保存在项目已被Git忽略的 `data/initial-state/<日期>/`，不进入Web `public/`、示例种子、测试夹具或构建产物。

- `baseline.json`：完整历史账本原始单元格及公式缓存、计入/排除标记、负债、账户、持仓数量来源、最新观察、资金约束及计划草稿。
- `holdings-api-preview.json`：只将最新截图中可表达的持仓投影到现有 `HoldingsBatchRequest`，用于后续导入预览；没有请求任何账号接口。历史负债、未知金额和历史基金净值仍留在完整批次中，不为迁就接口改成零或正资产。
- 历史全家庭净资产只属于历史基线；缺少同日估值、转账后余额及基金新份额时，全家庭当前净资产为空，不能给一个精确但错误的新总额。
- 截图收到日期不是行情时间。截图推算的成本与按日额推算的定投金额，保留为派生观察；不伪造成已确认成交价格、股数、费用和结算记录。
- 资金划转金额未知时，只记录账户关系与“内部划转、不新增本金”的事实，不倒推一笔转账。
- 历史基金份额表里的推算份额保持原始来源身份，不升级为券商确认份额。
- 计划价格、交易仓拆分、月度调度等建议参数标为研究草稿；用户确认的资金边界单列。保存初始状态不等于激活自动执行。

生成入口：`tools/bootstrap_portfolio.py --help`。该工具要求显式指定来源文件；只写本项目已忽略的data目录，同一批次重复运行不重复记录，不同内容不得静默覆盖。正式XLSX台账与现有数据库不改。

## 状态边界

| 对象 | 应保存的字段与职责 |
| --- | --- |
| 账户与资金池 | 所属人、机构、账户、币种、境内/境外、共享资金池；本金约束独立于每日市值 |
| 持仓及余额观察 | 数量/金额、各字段截至时间、来源、确认/推算/未知、结算及可用范围；零和未知分开 |
| 事实变更 | 用户确认、截图替换、实际成交、转账、分红、费用、结算；稳定来源指纹和修订关系 |
| 计划版本 | 生效时间、有效范围、目标、资金池、优先级、限价、股数上限、底仓/交易仓、冷却窗口、失效条件；保留历史版本 |
| 计划执行单 | 一项可执行意图关联计划版本，状态为待条件/可评估/已下单/部分成交/已成交/已结算/取消/跳过/到期/待补关键数据 |
| 成交与结算 | 实际账户、证券、方向、数量、价格、费用、币种、成交时间、券商订单/成交ID；多笔成交归属同一订单 |
| 行情与日历 | 价格时间、来源、是否参考/延迟、市场日历、基金申购日及确认日、公司事件；显示缺失与陈旧状态 |
| 任务及提醒 | 规则ID＋计划版本＋市场交易日＋触发阶段为去重键；确认、跳过、延后、已处理可追溯 |

不能将“计划记录”同时充当持仓事实和成交事实。未来扣款不能提前完成；成交不等于全部结算；卖出回款也不等于可立即取款。

## P0：先让记录与计算可信

1. **私有基线导入与一次性核对。** 预览来源、账户匹配、重复项、未知项；确认后建立切换时点及初始余额。未明确的数量允许按金额记录，但应说明不能进行精确股数建议。不能用当前成本为未知值的持仓填出零成本收益率。
2. **成交一次写入、事务内联动。** 新增独立执行入口，沿用GET/POST约定。验证账号和币种、券商成交指纹后，在同一数据库事务中写成交、调整持仓数量/成本、更新待结算及可用现金、占用/释放计划额度。任何一步失败全部回滚；更正用可追溯修订/冲销，不直接覆盖历史。
3. **防止快照与流水重复计算。** 以切换时点初始化余额，旧流水保持历史展示，不自动重放。后续截图对账只记录差异；不能在已扣现金之上再次扣同一笔成交。截图已反映的新持仓也不能再加一遍推算买入。
4. **区分资产、可下单余额与月度投入。** 买入需要同时满足账户可用资金、资金池约束和月度剩余额度。内部转账净投入为零；卖出释放原池资金，不能当新本金再复制一份预算。汇率按用途和日期保存，不能混用历史预算汇率与今日净值汇率。
5. **范围内的数据缺口。** 缺某银行的转账后余额，只限制依赖该余额的动作；不让全系统重复问同一问题，也不让无关账户的今日任务一起消失。

验收场景：一笔买入、分两次成交、重复导入、费用后到、卖出后回补、同币种内部转账、跨币种兑换、历史快照覆盖到同一笔交易、两个设备并发更正、负债与零余额。每种情况都核对现金、数量、成本、额度与修订来源。

## P1：计划驱动的今日页

将首页主要内容改为“今日安排”，资产总览留作第二层。

每条任务用普通语言说明：做什么、金额/数量上限、为什么、依赖哪份计划、哪些条件已满足、何时再评估。主操作为“记录成交”“确认扣款成功”“本次跳过”“延后处理”；不要只发一个没有后续动作的价格通知。

固定任务顺序：

1. 已确认完成：今天的定投或成交，避免重复下单。
2. 必须处理：影响现有仓位的失效/资金约束、失败扣款、待结算异常。
3. 满足全部条件后可评估：价格、止跌、事件窗口、数量、现金、月度额度同时通过。
4. 等待条件：尚未到价、未满观察日、财报暂停、数据质量不足，分别给出原因。
5. 明确无新增动作：告诉用户按计划保持持仓，减少为“完成任务”而交易的冲动。

任务状态由同一份已保存事实和计划生成；重新打开页面不重新采访用户。规则边界、市场时区和节假日要进入测试。个股需要已结束日线确认的信号，不能在当日盘中冒充确认完成；基金扣款日、份额确认日和净值日分别记录。

### 自定义计划的录入

允许自然语言、模板或表格输入，先转换为规则草稿，再展示一页可理解的规则预览：账户/资金池、周期与上限、条件、优先级、失效和有效期。一次激活后沿用，修改生成新版本。自然语言模型不得直接执行任意脚本或更改余额。

规则冲突按已明确的优先级解释：已成交事实优先于计划预估；明确资金约束优先；当月有范围的补充规则覆盖长期模板；同一笔资金不能同时被定投、额外买入和回补重复预留。没有明确覆盖关系的冲突产生一次待核任务，不默默选择一个版本。

### 计划外交易

下单前提供轻量检查：是否超出计划、占用后余额、同类集中度、本月其他安排受什么影响。选择继续时记录偏离原因，不能悄悄放宽原规则。**已经实际成交的计划外交易必须允许如实记录**，再生成偏离复盘；禁止因为超限而拒绝入账，导致系统账本与券商脱节。

## P2：可靠提醒与低负担对账

- 先实现应用内每日安排及待办数量，再接Android/浏览器或其他已选择通道；本轮不在Codex另建定时自动化代替产品实现。
- 一天只发一份可行动摘要；同条件不重复提醒。条件由未满足变为满足、任务异常或发生重大变化才追加提醒。
- 参考、陈旧或时间不明行情只提示更新，不能发出已满足买卖条件的通知。接入报价源时验证授权范围、频率、时区、停牌及拆股，不把现有刷新接口当作已完成接入。
- Android定投Worker生成计划执行单，成功需来自用户确认或券商/基金的实际确认记录；设备重启、重试、离线恢复不能生成重复成功。
- 截图/券商CSV先预览变化、疑似重复和本次增量，确认后联动入账；无精确成交时只记余额/数量观察，不还原不存在的成交明细。
- 月末只问新增缺口，自动汇总定投执行、预算差异、计划外操作、剩余资金及下月草案；不把未花完额度自动变成追补义务。

## 分端实施顺序与交付边界

| 顺序 | Server | Web | Android |
| --- | --- | --- | --- |
| 第一批 | 事实/观察与计划版本、基线导入预览、切换时点、成交原子联动及回归 | 基线核对、统一成交表单、完成后同快照刷新 | 对齐持仓/成本/现金语义、备份迁移兼容 |
| 第二批 | 确定性规则评估、额度预留、任务状态和必要缺口 | 今日页、计划编辑预览、成交/跳过/延后、偏离记录 | 今日页与同一任务ID，本机缓存与同步冲突 |
| 第三批 | 行情质量、事件日历、通知出站队列与去重 | 提醒设置、导入对账、月末复盘 | 通知权限、Worker重试去重、离线补同步 |

不为这一轮引入新的Agent框架或另一个账本。服务端拥有Web计算正本；Android复用规则契约，确需离线计算时使用跨端共用用例验证。保留现有未提交的入口/显示名称改动，本轮不借整改重写这些实现。

完成标准是用户能连续走通“保存计划 → 每天看到安排 → 记录成交一次 → 数量/现金/剩余额度一致 → 提醒不重复 → 月末只核新增缺口”，不能用新增一个AI聊天入口代替此流程。
