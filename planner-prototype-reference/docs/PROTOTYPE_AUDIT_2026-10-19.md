# FinUnity 最终方案与原型评审

评审日期：2026-10-19 起，至 2026-10-20 完成（Asia/Shanghai；8011 实测在 2026-10-19 晚间完成）。
评审对象：[`docs/final/FINAL_PLAN.md`](final/FINAL_PLAN.md) 与 `docs/final/images/` 六张原型图，以及它们所描述的现有原型（`frontend/src/planner/`、`backend/app/planner/`）。
这份文档没有改动产品源码、`docs/final/`、测试和数据库；新增的只有本文件与 [`docs/audit-2026-10-19/`](audit-2026-10-19/)。

## 一、结论

**能执行吗？** 分三层看：

1. **方案的范围、规则和技术边界：成立。** 「资金用途标记不是转账」「预测不入账」「应急预留优先」「完成由事实驱动」这些规则前后一致，后端也真的做到了（Decimal、幂等键、乐观版本、批量原子性、作废留痕）。
2. **现有原型的主干闭环：能走通。** 8011 上现有的数据（一份使用中的方案、一笔已记录的投入、一份本月复盘）说明「建档 → 测算 → 确认 → 记投入 → 复盘」这条链路确实走通过。我没有在 8011 上做任何写操作；跨月、重设基准等情形是在隔离库上复现的。
3. **但按「一个真实家庭每月用一次」来检验，闭环有三处会卡住或丢数据**——这是需要先改、才算「可执行」的部分：
   - **P2** 新用户走「开始建档」时，建档日期默认是今天，而记账日期必须晚于它、又不能是未来 → **当天一条「已发生」都记不进去**。示例数据把日期放在昨天，恰好绕开了。
   - **I1 / I2** 未保存的建档修改，会被任何一次测算、记账、作废、刷新**静默清空**；执行页的记账草稿，切到别的页再回来就没了（实测）。
   - **P1 / P3** 月度时间窗：跨月后没有新月份的行动，**上月复盘只能在当月内做，过了月底就再也生成不了**；而一次「重设基准」（再保存建档并确认新方案）会让当月已记录的投入从进度和复盘里消失。

另外两件事需要知道：

- 首页最显眼的数字有误导：**「可动用现金 ¥98,000」其实是账户现金总额**，扣掉应急预留 ¥30,000 和已分给目标的 ¥20,000，真正可自由安排的是 **¥48,000**（后端已经算出来了，界面没用）（N1）。
- **评审材料撑不起它自己列出的审核点**：五张图被折叠线截断，「目标进度、缺口、本月行动、确认方案」在图里看不到（D1）。

**共 36 项**：阻断 2、高 10、中 13、低 11。其中产品问题 32 项，纯前端能解决 25 项，需要后端小改 4 项，需要先定产品口径再改后端 3 项（P1、P3、P4）。

**值得保留的**：资金规则本身；批量保存的原子性与幂等；作废保留审计；记录表单里「增加/减少 + 账户两端变化预览」；文案里「测算不是收益承诺」「AI 未配置时手动流程仍可用」这类诚实的边界声明。

**优化稿**（按你的要求，用前端 Skill 做的）：[`audit-2026-10-19/optimized-prototype/index.html`](audit-2026-10-19/optimized-prototype/index.html)。一个自包含的可交互原型，沿用项目自己的 Editoriale 设计令牌，逐条对应下面的编号。详见第六节。

### 阻断：会丢数据，或让一个流程在第一天就走不通（2 项）

#### P2 · 阻断 · 建档日期默认「今天」，当天无法记任何已发生的账

- **位置**：`schemas.py:92`（as_of 默认今天）、`service.py:282`（BEFORE_ANCHOR）、`schemas.py:222`（不能是未来）、`execution.ts:122-125`
- **证据**：隔离库复现（`lifecycle_check.py`）、读源码
- **现象与原因**：新用户走「开始建档」时建档日期默认今天；记录日期必须晚于账户日终基准，又不能是未来 → 当天一条都存不进去（422 BEFORE_ANCHOR）。示例数据把日期定在昨天，恰好绕开了这个坑。
- **建议 / 优化稿的处理**：「余额截至」默认昨天、日期选择器上限=昨天并说明原因；记账日期早于基准时，错误里直接给出「去校准余额」的出口。
- **需要后端配合**：否（纯前端）

#### I1 · 阻断 · 未保存的建档修改会被任何操作静默清空

- **位置**：`PlannerApp.tsx:865`、`PlannerApp.tsx:909-924`
- **证据**：8011 上实测、读源码
- **现象与原因**：测算、生成方案、确认、记账、作废、刷新都会重新读取并覆盖建档草稿（PlannerApp.tsx:865）。在 8011 上改名称后点「测算这个情景」，回来已还原，没有任何提示。
- **建议 / 优化稿的处理**：建档草稿独立存放，刷新与其它操作都不碰它；有修改时顶部显示「N 处未保存」并可放弃/保存；离开页面前确认。
- **需要后端配合**：否（纯前端）

### 高：数字或流程会误导人 / 让月度闭环卡住（10 项）

#### P1 · 高 · 月度闭环的时间窗走不通：跨月后没有行动、上月复盘被拒

- **位置**：`service.py:256`（确认时只生成当月行动）、`service.py:604`（CURRENT_MONTH_ONLY）、`PlannerApp.tsx:945`、`ExecutionPanel.tsx:96`
- **证据**：隔离库复现（`lifecycle_check.py`）、读源码
- **现象与原因**：行动只在确认方案时生成当月的一份；跨月后执行页只写「确认方案后显示本月计划」，且复盘只允许「当月」，10 月的复盘过了 10 月就再也生成不了。
- **建议 / 优化稿的处理**：月初出现「沿用方案、生成本月计划」一键续期（仍由你确认）；月初 10 天内可补做上月收官复盘；月末前 4 天出现复盘提示。
- **需要后端配合**：需要（规则或接口要改，先定产品口径）

#### P3 · 高 · 重设基准后，当月已记录的投入从进度和复盘里消失

- **位置**：`service.py:492`（action_view 排除 ≤ 基准日）、`service.py:641`（review 同样排除）
- **证据**：隔离库复现（`lifecycle_check.py`）、读源码
- **现象与原因**：再次保存建档并确认新方案后，10-19 记过的 ¥2,000 被排除（因为早于新基准日）：行动回到「待投入 ¥0 / 还需 ¥2,000」，复盘实际为 ¥0。
- **建议 / 优化稿的处理**：进度只看「本月已发生的新增投入」，与建档基准日解耦；余额仍按基准日重放，二者各算各的。
- **需要后端配合**：需要（规则或接口要改，先定产品口径）

#### P4 · 高 · 没有轻量的「对账」：校准余额只能改建档

- **位置**：`engine.py:73-113`（余额 = 基准 + 重放流水）；`schemas.py` 的 Occurrence 没有「对账/校准」类型
- **证据**：读源码、推断
- **现象与原因**：余额 = 基准 + 已记流水。只记一部分流水，现金就会逐渐偏离银行里的数字；唯一的校准办法是改建档，而这会使方案过期（P5）并触发 P3。
- **建议 / 优化稿的处理**：账户旁增加「对账」：填银行里的实际余额，生成一条可作废的「差额调整」，基准日不动。
- **需要后端配合**：需要（规则或接口要改，先定产品口径）

#### P5 · 高 · 待确认方案过期了没有任何提示，确认只会报错

- **位置**：`service.py:226`、`service.py:238`、`PlannerApp.tsx:943`、`PlannerApp.tsx:1287`
- **证据**：隔离库复现（`lifecycle_check.py`）、读源码
- **现象与原因**：账目一变，旧草案仍标「待确认」且「确认」可点；点下去 409，错误出现在页面顶部；失效的草案永远留在「方案版本」里。
- **建议 / 优化稿的处理**：草案显示「已过期」、确认禁用，旁边给「基于最新账目重新测算」；旧草案自动收进历史，也可手动放弃。
- **需要后端配合**：小改（接口多返回一个字段或状态）

#### N1 · 高 · 「可动用现金 ¥98,000」其实是账户现金总额

- **位置**：`engine.py:293`（unallocated_cash）、`PlannerApp.tsx:1034-1037`
- **证据**：8011 上实测、读源码
- **现象与原因**：它和「应急预留 ¥30,000」并排，读起来像又多了 ¥98,000 可用。扣掉应急预留与已分给目标的钱，真正可以自由安排的是 ¥48,000——后端已经算出（unallocated_cash），界面没用。
- **建议 / 优化稿的处理**：首屏大数字改为「可自由安排 ¥48,000」，下面用资金分层条拆成 应急预留 30,000 + 已分给目标 20,000 + 可自由安排 48,000。
- **需要后端配合**：否（纯前端）

#### N2 · 高 · 复盘用「¥0.00」表示「没有记录」，月中还显示「差额 −¥3,000」

- **位置**：`PlannerApp.tsx:805-830`（ReviewCard）、`service.py:655`、`schemas.py:398`
- **证据**：8011 上实测、读源码
- **现象与原因**：与文档里「未知不是零」「无记录不代表实际为零」相反；partial_month 字段后端有、前端没用，月中就把进行中当成未达成。
- **建议 / 优化稿的处理**：没有记录显示「未记录」；月中显示「进行中 · 还剩 N 天」，月末之后才说「未达成」。
- **需要后端配合**：否（纯前端）

#### I2 · 高 · 执行页的草稿切换标签就丢

- **位置**：`ExecutionPanel.tsx:64`、`PlannerApp.tsx:1324-1350`
- **证据**：8011 上实测、读源码
- **现象与原因**：草稿放在只在该页挂载的组件里（ExecutionPanel.tsx:64），切到别的页再回来已清空——正好是「最多 50 条批量录入」最怕的事。
- **建议 / 优化稿的处理**：草稿自动保存在本机，切页、刷新、关抽屉都还在；抽屉里写明「草稿已自动保存」。
- **需要后端配合**：否（纯前端）

#### I3 · 高 · 反馈离操作太远；批次失败不定位到那一条

- **位置**：`PlannerApp.tsx:989-1006`、`service.py:431`
- **证据**：8011 上实测、读源码
- **现象与原因**：成功/错误条固定在页面顶部（实测提示在 y≈33，按钮在 y≈617）；后端返回了 item_index，界面没用来定位草稿。
- **建议 / 优化稿的处理**：保存后在对应计划卡高亮并弹出就近提示；失败时定位到出错的那一条与那个字段。
- **需要后端配合**：否（纯前端）

#### I4 · 高 · 试算里填的数被「已有定投」静默覆盖

- **位置**：`engine.py:220`、`PlannerApp.tsx:1208-1210`

## 六、优化稿（前端 Skill 产出）

**位置**：[`docs/audit-2026-10-19/optimized-prototype/index.html`](audit-2026-10-19/optimized-prototype/index.html)（250 KB，双击即可打开，离线可用，字体内嵌）。

**它不是什么**（请按这个口径使用）：

- 标为「需要」「小改」的几处（P1、P3、P4、P5、N7、N8、N9）在原型里是**按期望行为演示**的，落地要先改后端。
- 没有在 Safari / Firefox、屏幕阅读器、真机触屏上验证；手机是 390 宽的视口模拟。

## 七、建议的落地顺序

1. **先做纯前端（不碰后端，风险最低）**：I1（建档草稿不要在 `refresh()` 里被覆盖：只在首次加载与保存成功后赋值）、I2（记账草稿上提或存 localStorage）、I3、I4、I5、I7、I8、I9、I10、I11、I13、I15、I16；数字与文案 N1–N6；P2 的前端部分（默认昨天 + 日期上限 + 引导文案）。其中 I1、I2、P2 最优先。
2. **后端小改**：N7（接口返回「建档修订号」，普通记账不再触发提示）、N8 / N9（返回「补缺口」三个杠杆；`needed_monthly` 向上取整）、P5（方案增加 stale 状态与放弃接口）。
3. **先定产品口径、再改后端**：
   - P1：跨月是「沿用方案一键续期（仍由用户确认）」，还是继续要求重新测算？上月复盘窗口放到几天？
   - P3：进度是否与基准日解耦（建议：进度只看「本月已发生的新增投入」，余额仍按基准日重放）。
   - P4：对账记录是新类型，还是复用「收入/支出」加标记？
4. **文档与验收**：重出评审用图（整页 + 关键状态）；把 `lifecycle_check.py` 的 A–E 改写成 pytest 回归（修复后期望值要改写）；补组件级回归；统一用语（第五节）。

## 八、没有验证的、以及假设

- 没有测多人、公网、迁移、真实收费模型调用，这些本来也不在本阶段范围内。
